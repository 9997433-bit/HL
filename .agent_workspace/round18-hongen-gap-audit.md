## 4. 审计发现（探针结构与实现坑，实现岗务必先读）

- **A. H2 的去重门是「全库」口径**：现 940/940 全不撞句，新写 260 条既不能互相复制、也不能撞旧 940 条。seed 在 `apps/literacy-app/scripts/data/char-play-seed.txt`（现 1096 行、覆盖 u1–u55），正确姿势仍是**扩 seed → `npm run gen:play:rich`**，富库文件头声明勿手改。940→1200 即续到约 **u75**（每单元 16 字）。
- **B. H3 的两个消费点都要改**：`char-play.js` L41 的 `import * as richModule`（富库注册主链）和 `char-intro.js` L23 的 `getRichPlay`（认步引用）。拆包后 `countRichPlays()` / round15–17 的旧探针仍要能在 Node 侧数出全量——建议「分片数据 + 同步索引（char→unit 映射，轻量）+ 运行时 `import()` 取片」，旧探针改走聚合入口。`check:bundle` 预算与 H8 回归是这条的双保险。
- **C. H4 的 56 道不一致有三种病因，别一刀切改 steps 字段**：① `analyzeEquation` 拆不出第三步（`sum-times` 系 3→2、`meet`/`minibus` 3→2）——该修解析器识别复合式；② 有余数除法被并成一步（`div-remainder` 2→1）——商与余数应是两步；③ 声明偏小（`average` 2→3）——该改母题 `steps`。修完必须全量重跑（214 道 `make(seed)` 后 `buildAnalysis`），皮肤展开的语义模板一条剖析对多个 id，改一处过一族。
- **D. H5 与 H4 是同一批文件，先对齐再扩写**：手写链的 steps 是「一个函数写一步」，与 `analyzeEquation` 拆出的步骤**按序号一一对应**——若 #6 改了解析器步数，已有 50 条手写链的函数数组会错位。**编排上 #6 先行合入、#7 基于对齐后的步数扩写**，否则 80 条里混入错位文案。两条硬约束继续生效：判题前不泄答案（asked 步不报得数）、语义模板文案不点名具体名词（只用 `question.unit`）。
- **E. H6/H7 证据必须本轮落盘**：`evidence/r18/` 现为空。四图口径：富玩关卡 / 拆包后单字详情（网络面板或构建产物佐证分片加载）/ 剖析步数对齐 / 周报或学伴。H7 不得复用 r17 报告——重跑 `android:sim` 或诚实 BLOCKED（含复现命令）。
- **F. H8 起点即绿是本轮红利也是责任**：与 R16/R17 开局「借旧报告弱绿」不同，这次 `check:round17` 在干净基线上 8/8。任何岗把它改红（尤其 #5 拆包动 `char-play-rich.js` 结构、#6 动 `wpAnalysis.js` 导出）都算退化，先跑 `check:round17` 再提交。
