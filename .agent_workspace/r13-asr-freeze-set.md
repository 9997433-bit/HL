# Round 13 H1 · 跟读离线 ASR 儿童冻结集（骨架 56 条 → 实录 300 条）

> 数据：`apps/literacy-app/scripts/data/asr-eval-set.json`（`freezeSet` 段 + `speakers[]` + `clips[]`）
> 跑道：`apps/literacy-app/scripts/test-asr-eval-set.mjs`（`npm --prefix apps/literacy-app run test:asr:evalset`）
> RTF 基准：`.agent_workspace/r13-asr-android-rtf-baseline.md`
> 上游口径：`.agent_workspace/r9-followread-asr-evaluation.md` §5 · `.agent_workspace/r11-asr-eval-set.md`
> 判定：`apps/literacy-app/public/asr/manifest.json` 的 `freezeChecklist` 与 `goNoGo`
>
> **本轮结论：`available` 仍是 `false`。** 骨架不是录音，推算不是实测。
> 这份文档要讲清的是另一件事：为什么现在可以开录了，以及开录时每一条要往哪一格里填。

## 1. 这一轮改变了什么

R12 把 35.31 MiB 的模型逐文件落进了仓库，从那以后卡住放行的只剩两条：

| 冻结项 | R12 结束时 | R13 结束时 | 还差什么 |
|---|---|---|---|
| F4 儿童冻结集 | 36 条占位，够跑管线，不够开录 | **56 条骨架**，按 300 条配额等比缩样，同意/配额/上限都进了结构 | 实录 0/300 |
| F7 真机性能 | 一个数都没有 | **主机基准 + 真机可复算的推算路径** | 真机 0 台 |

两条都还是 `todo`，`goNoGo.verdict` 还是 `no-go`。变化在于：F4 从「没人知道该录什么」变成「拿着这张表就能开录」，
F7 从「等真机」变成「等真机，但已经知道大概率会顶在哪条线上」。

R11 那 36 条的问题不是少，是**形状不对**：它是「每一格至少落一条」的最小骨架，
`normal` 占 42%、`initial` 只有 2 条。真按这个形状扩到 300 条，最后会发现某些格子里的样本
在统计上撑不起子组比较，而重录一批孩子的成本远高于现在把表排对。

## 2. 骨架现状（56 条 / 18 个说话人 / 16 首诗）

### 2.1 按 300 条配额等比缩样

`freezeSet.categoryQuota` 写的是 300 条时每类的目标条数；骨架按 `56/300` 等比缩样，
再打 `skeletonFloorRatio = 0.6` 的折当作硬地板（harness 现算，缩回去当场红）：

| 类别 | 300 条配额 | 等比 = 配额 × 56/300 | 硬地板（×0.6） | 现有 | 它守的是什么 |
|---|---|---|---|---|---|
| `normal` 读全对 | 150 | 28.0 | 17 | 25 | 字符召回的主分母 |
| `miss` 漏字 | 45 | 8.4 | 5 | 9 | 漏字检出召回 |
| `extra` 多读 | 20 | 3.7 | 2 | 4 | 多读只轻罚，不判读错 |
| `repeat` 重复 | 15 | 2.8 | 2 | 3 | 重复不该被当成漏读 |
| `silence` 没出声 | 25 | 4.7 | 3 | 5 | 静音误判率 |
| `bystander` 旁人说话 | 15 | 2.8 | 2 | 3 | 别人的声音不算孩子读了 |
| `tone` 声调错 | 20 | 3.7 | 2 | 4 | 诊断层正样本 |
| `initial` 声母错 | 10 | 1.9 | 1 | 3 | 诊断层正样本 |

`tone`/`initial` 现有 4/3 条，高于等比值——R11 §7 记过这个债：诊断层要谈精确率，
这两类得单独扩到 30 条以上，骨架先把位子占大一点，省得扩样时忘了它们。

### 2.2 其余维度

| 维度 | 300 条配额 | 骨架实际 | 偏差 |
|---|---|---|---|
| 划分 | dev 40% · threshold 30% · final 30% | 22 / 17 / 17 条 = 39.3% / 30.4% / 30.4% | 容差 ±8 个百分点内 |
| 环境 | 安静 50% · 电视 30% · 远讲 20% | 28 / 17 / 11 条 = 50.0% / 30.4% / 19.6% | 基本贴合 |
| 设备 | 手机 67% · 平板 33% | 37 / 19 条 = 66.1% / 33.9% | 基本贴合 |
| 年龄 | 4–6 与 7–9 各半 | 29 / 27 条（说话人 9 / 9 人） | 基本贴合 |
| 性别 | 各约一半 | 女 31 / 男 25 条（说话人 10 / 8 人） | 骨架阶段可接受，扩样时补男孩 |
| 口音 | 不设配额，但不许单一 | 标准 5 · 北方 4 · 南方 5 · 西南 4 人 | 四类都在 |
| 说话人 | ≥40 人，单人 ≤12 条 | 18 人，单人最多 4 条 | 人数是扩样阶段的事 |
| 语料 | 不许挤在几首诗上 | 16 首（`poems.js` 共 24 首） | 下限 12 首，harness 守 |

三份划分**说话人零重叠**（dev 7 人 / threshold 6 人 / final 5 人），每份都自带
静音或旁人说话的负样本，也都同时有两个年龄段、两种性别、两种以上口音、两种设备、三种环境——
否则子组差距（F6 的 `subgroupGap`）在那一份里根本算不出来。

## 3. 骨架里新增的结构（R13）

R11 的条目字段只够跑管线，不够开录。这一轮补上的是**录制真正会绊倒人的那几件事**：

```jsonc
// speakers[] 每人新增
"consent": "pending"        // pending | signed | withdrawn

// 顶层新增
"freezeSet": {
  "id": "FS-2026-09-zh-poem",   // 批次号：将来横比分数时要认这个
  "stage": "skeleton",          // skeleton | recording | frozen
  "skeletonFloor": 50,          // 骨架地板；与 minClips、清单 evalSet.minClips 三处对齐
  "recordedFloor": 300,         // 冻结地板 = targetClips
  "recorded": 0,                // 现算核对，不许手写
  "maxClipsPerSpeaker": 12,     // 单人上限，防某个孩子的口音主导分数
  "minPoems": 12,               // 语料横跨下限
  "splitQuota": { ... },        // 划分配额 + splitTolerance 容差
  "categoryQuota": { ... }      // 300 条时的类别配额 + skeletonFloorRatio 折扣
}
```

`harness` 对这几个字段的守法（`ROUND13_H1` 那五条断言）：

1. **进度不许手写。** `freezeSet.recorded` 必须等于 `clips[]` 里 `status === "recorded"` 的实际条数；
   `stage` 只有在实录 ≥300 条时才允许写成 `frozen`，否则 `available` 必须是 `false`。
   这条挡的是最省事也最致命的作弊：把「已录 200 条」写进 JSON，而一条音频都没有。
2. **骨架不许缩水。** 条数 ≥50，且 `minClips`、`freezeSet.skeletonFloor`、清单 `evalSet.minClips` 三处必须是同一个数。
3. **同意状态先于录音。** 每个孩子必须有合法同意状态；没签（`pending`）就不许出现他的 `recorded` 条目；
   撤回（`withdrawn`）的孩子连占位条目都不许留——撤回是要能真的执行的，不是写在文档里的承诺。
4. **单人不许超配。** 任何孩子超过 `maxClipsPerSpeaker` 条当场红。
5. **配额不许失衡。** 划分比例超出容差、任何一类掉到等比地板以下，都红。

## 4. 从 56 条骨架到 300 条实录

一条片段的生命周期没变（见 `r11-asr-eval-set.md` §4），变的是开录前后的门：

**开录前（`stage: skeleton` → `recording`）**

1. 家长书面同意逐份签回，签一个把那个孩子的 `consent` 改成 `signed`。
   撤回通道要真的能走：改成 `withdrawn` 之后，harness 会强制那个孩子的条目清零。
2. 录音存到仓库外的受控目录，去标识化编号（孩子只以 `S01` 这样的编号出现）。
3. 说话人扩到 ≥40 人。18 人撑不起单人 ≤12 条 × 300 条的配额，这是扩样的第一优先级。

**录制中**

4. 只往每一格里填，不重排格子——这正是这一轮把配额表定死的目的。
   每录满一批就跑一次 harness，配额跑偏当场看得见。
5. 双标注 + 第三人仲裁，`status` 改 `recorded`、补 `labels`、**删掉 `mock`**。
   harness 断言 `recorded` 的条目不许残留模拟转写：真假指标混进一张表是最容易骗到自己的地方。

**冻结后（`stage: frozen`）**

6. `test-asr-eval-set.mjs` 把 `clips[].mock` 换成引擎输出，同一个聚合器直接出 F5 文本层的真实指标。
7. 文本层达标 + 诊断层达标 + 真机性能达标（F7）+ 离线重启达标（F9）→ `goNoGo.verdict` 才可能变 `go`，
   `available` 才可能变 `true`。**这四步一步都不能跳。**

## 5. 现在跑出来的数字都是什么

`npm --prefix apps/literacy-app run test:asr:evalset` 这一轮 33/33 项通过、7 场故障演练全绿。
但报表里的数要分三类读：

| 类 | 例子 | 能说明什么 |
|---|---|---|
| **实测** | 整包 35.31 MiB、降档耗时 601 ms、跨源请求 0 次、五类故障演练 5/5 | 真跑出来的，进 Go/No-Go 判定 |
| **模拟** | 安静集 95.8%、噪声集 90.8%、漏字检出 100%、静音误判 0% | 用我们自己写的 `mock` 算的，**不是模型指标**；只证明聚合器算得对 |
| **主机** | RTF p95 0.276、句末 7.4 ms、内存 +385 MiB | 在 CI VM 上量的，`value` 恒为 `null`，只作参考，见 §RTF 文档 |

三类在报表里分别显示为「实测 / 模拟 / 主机（不计入）」。混着读会得出「跟读已经能用了」这种结论，
而实际上文本层一个真实数字都还没有。

## 6. 已知局限

- **56 条撑不起任何统计结论。** 它撑得起的是「格子排对了、管线跑得通、开录不用返工」。
- **模拟转写没有代表性。** `mock` 是我们写的，对儿童共发音、拖音、气声这些真实错误模式一无所知。
- **说话人只有 18 人。** 单人 4 条看着安全，但 18 人的口音分布本身就是偏的；
  扩到 40 人之前，任何子组差距都不要当真。
- **性别略偏。** 女 10 人 / 男 8 人，条数 31 / 25。扩样时优先补男孩，否则 F6 的性别子组会先撞线。
- **录音伦理与合规流程仍未成文。** 同意书模板、撤回通道的操作手册、删除时限的执行记录——
  这是 F4 真正的长尾，比录音本身更花时间。这一轮只把「同意状态」做进了数据结构，
  没有把流程文档写出来。
