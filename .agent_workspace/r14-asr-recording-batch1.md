> 跑道：`apps/literacy-app/scripts/test-asr-eval-set.mjs`（`ROUND14_H1` 五条断言 + 一条 post）
> 冒烟：`apps/literacy-app/scripts/smoke.mjs`（`ROUND14_H1_SMOKE`）
> 上游口径：`.agent_workspace/r13-asr-freeze-set.md` · `.agent_workspace/r11-asr-eval-set.md` §4

## 1. 这一轮改变了什么

R13 结束时，F4 从「没人知道该录什么」变成「拿着这张表就能开录」。可真要派工，
还差两件很实际的事：**没人知道第一批录哪 100 条**，以及**录回来该由谁、按什么规矩收下**。

| | R13 结束时 | R14-1 结束时 | 还差什么 |
|---|---|---|---|
| 槽位 | 58 条骨架，按 300 条配额等比缩样 | **批次 1 的 100 个槽位全部排定**，每条挂 `batch: "B1"` | B2/B3 只留号段（C101–C300），未排位 |
| 说话人 | 18 人 | **30 人**（dev 12 / threshold 9 / final 9） | 300 条要 ≥40 人，还差 10 人 |
| 落库 | 无。录回来靠人手改 JSON | **`ingest-asr-freeze-batch.mjs`**：14 条拒收闸 + 演练 / 落库两档 | 真交付 0 份 |
| 同意 | 结构里有 `consent` 字段 | 落库闸把它变成**硬前置**：没签回就收不下 | 同意书 0/30 签回 |
| 实录 | 0/300 | **0/300** | 录音本身 |

第三行是这一轮真正的东西。前两行是数据，第三行是**规矩能不能被执行**：
「双标注 + 第三人仲裁」写在 R13 文档里是一句承诺，写进落库闸之后它才是一道门。

## 2. 批次 1 的 100 个槽位是怎么排的

300 条拆三批，每批 100 条。批次 1 的每一格都按 **300 条配额的三分之一**站位——
录的时候只往格子里填，不重排格子。

### 2.1 类别（八类异常）

| 类别 | 300 条配额 | 等比 = 配额 ÷ 3 | 批次 1 实排 | 为什么这么排 |
|---|---|---|---|---|
| `normal` 读全对 | 150 | 50.0 | **46** | 字符召回的主分母；让出 4 条给诊断层 |
| `miss` 漏字 | 45 | 15.0 | **15** | 漏字检出召回 |
| `extra` 多读 | 20 | 6.7 | **7** | 多读只轻罚，不判读错 |
| `repeat` 重复 | 15 | 5.0 | **5** | 重复不该被当成漏读 |
| `silence` 没出声 | 25 | 8.3 | **8** | 静音误判率 |
| `bystander` 旁人说话 | 15 | 5.0 | **5** | 别人的声音不算孩子读了 |
| `tone` 声调错 | 20 | 6.7 | **9** | R13 §2.1 记的债：诊断层要谈精确率，这两类得先攒够 |
| `initial` 声母错 | 10 | 3.3 | **5** | 同上 |

`tone`/`initial` 合计排了 14 条（等比 10 条）。这是有意超配：F6 谈的是精确率，
两类各自要到 30 条以上才撑得起一个百分比，三批平摊只会三批都不够。多出来的 4 条从
`normal` 里让——`normal` 的分母本来就最厚，少 4 条不影响字符召回的稳定性。

### 2.2 其余维度

| 维度 | 300 条配额 | 批次 1 实排 | 说明 |
|---|---|---|---|
| 划分 | dev 40% · threshold 30% · final 30% | **40 / 30 / 30 条** | 正好落在配额上，容差 ±8 个百分点没用上 |
| 环境 | 安静 50% · 电视 30% · 远讲 20% | **50 / 30 / 20 条** | 同上 |
| 设备 | 手机 67% · 平板 33% | **67 / 33 条** | 同上 |
| 年龄 | 4–6 与 7–9 各半 | **52 / 48 条**（说话人 15 / 15 人） | 贴合 |
| 性别 | 各约一半 | **女 42 / 男 58 条**（说话人 13 / 15+2 人） | R13 记的债：骨架偏女，这一批反向补男孩 |
| 口音 | 不设配额，但不许单一 | 标准 26 · 北方 25 · 南方 26 · 西南 23 条 | 四类都在，且大致均分 |
| 说话人 | ≥40 人，单人 ≤12 条 | **30 人**，单人 2–5 条 | 人数还差 10，留给批次 2 |
| 语料 | 不许挤在几首诗上 | **24 首**（`poems.js` 全库） | 从 16 首铺到 24 首，每句诗最多被用两次 |
| 时长 | 3–10 秒 | 3.6–5.4 秒 | 五言/七言单句，落在区间中段 |

三份划分仍旧**说话人零重叠**（dev 12 人 / threshold 9 人 / final 9 人），
每份都自带静音或旁人说话的负样本，也都同时有两个年龄段、两种性别、两种以上口音、
两种设备、三种环境——否则 F6 的 `subgroupGap` 在那一份里根本算不出来。

## 3. 一条槽位就是一条派工单

槽位不是「去录 100 条」，是 100 条可以直接发给录音现场的指令。`C037` 这一条读作：

```jsonc
{ "id": "C037", "speaker": "S13", "env": "quiet", "device": "phone",
  "poem": "feng", "line": 0, "seconds": 4.3, "category": "normal",
  "spoken": "解落三秋叶", "mock": "解落三秋叶",
  "status": "placeholder", "audio": null, "batch": "B1" }
```

> 找 **S13**（4–6 岁 · 男 · 北方口音 · dev 组），**安静房间**，**用手机**，
> 读《风》第一句「解落三秋叶」，**照着读完整句**，约 4 秒。

异常类别的槽位额外写清「怎么读错」：`miss` 的 `spoken` 已经把要漏的那个字去掉了
（`C060` 是「云深不知处」漏成「云深知处」），`tone`/`initial` 的 `mock` 写的是
预期会被听成什么。**这些是设计意图，不是标注结果**——真录出来是什么样，以仲裁定稿为准，
和槽位对不上时由落库闸重新归类（见 §5 的 `category-mismatch` 与 §6 的类别漂移）。

## 4. 交付清单长什么样

录音现场交回来的是一份 JSON（连同仓库外受控目录里的音频），不是一堆散文件：

```jsonc
{
  "schema": "literacy-asr-freeze-delivery/1",
  "freezeSetId": "FS-2026-09-zh-poem",
  "batch": "B1",
  "deliveredAt": "2026-09-12",
  "consent": [
    { "speaker": "S13", "state": "signed", "formRef": "consent/S13-2026-09-01.pdf" }
  ],
  "clips": [
    {
      "clipId": "C037",              // 必须是批次 1 里已排好的槽位号
      "speaker": "S13",              // 必须和槽位排的是同一个孩子
      "audio": "B1/S13/C037.wav",    // 受控目录下的相对路径；绝对路径/../ 一律拒收
      "sha256": "…64 位…",           // 换了文件就换指纹，日后横比分数认这个
      "seconds": 4.3,
      "sampleRate": 16000,
      "category": "miss",            // 可选：录出来和槽位排的不一样时才写
      "labels": {
        "a": "解落三秋叶",            // 标注员 A
        "b": "解落三秋",              // 标注员 B
        "arbiter": "解落三秋叶"       // 两位不一致时必填，且只能在 A/B 两版里挑一版
      }
    }
  ]
}
```

字段少得刻意：**能从槽位查到的都不重复写**（诗、句号、环境、设备都在 `clips[]` 里），
交付方只负责回答「录到了什么」。重复写一遍只会多一处对不上的机会。

可以直接拷走的一份在
`apps/literacy-app/scripts/fixtures/asr/delivery-b1-example.json`——三条各示范一种情形：
两位标注一致、两位不一致走仲裁、录出来和排的类别不一样。harness 每次都拿它过一遍闸
（`ROUND14_H1` 第六条断言），所以它不会和工具走散。里面的 `sha256` 是编的、音频文件不存在，
`--verify-audio` 一定红——它只回答「一份合格的交付长什么样」。

## 5. 落库闸拦的是什么

`ingest-asr-freeze-batch.mjs` 有 14 条拒收码。每一条对应一种
「看上去像录完了、其实不算数」的情形，不是随手加的字段校验：

| 拒收码 | 拦的是什么 | 为什么值得单独一条闸 |
|---|---|---|
| `duplicate-in-delivery` | 同一条在交付里出现两次 | 数出来的 100 条里有两条是同一段音频 |
| `unknown-slot` | 交的号不在批次计划里 | 「顺手多录了几条」= 配额外的样本，会把类别比例带偏 |
| `wrong-batch` | 交的是 B2/B3 的号段 | 批次是横比分数的单位，串批等于串了对照组 |
| `already-recorded` | 槽位已经落过库 | 静默覆盖会让旧分数无从复现；重录要先作废旧的那一条 |
| `speaker-mismatch` | 换了个孩子来录 | 换人等于换子组，F6 的年龄/性别/口音分组立刻失真 |
| `consent-missing` | 同意书没签回 / 已撤回 | **录音伦理的硬前置**；撤回通道要真能执行，不是文档里的承诺 |
| `audio-in-repo` | 音频路径指向仓库 | 孩子的声音不进 git。绝对路径、`../`、`apps/` 开头一律拒收 |
| `audio-fingerprint` | 没有合法 sha256 | 没指纹的音频，换掉了没人发现 |
| `duration-out-of-range` | 不在 3–10 秒内 | 与评测集 harness 的同一条线；太短测不出、太长不是跟读 |
| `sample-rate-too-low` | 低于 16 kHz | 重采样只会把高频伪影当特征喂给 16 kHz 的流式模型 |
| `single-annotation` | 只有一位标注员 / 不一致却没仲裁 | 单标注的错误率进不了误差分析，双标注不是走过场 |
| `arbiter-not-a-choice` | 仲裁写了第三版 | 仲裁是**在两版里挑一版**；凭空另写一版是事后编答案 |
| `category-mismatch` | 定稿转写和类别对不上 | 最难查的一种错：`miss` 的分母里混进读全对的样本，报表上看不出来 |
| `speaker-over-cap` | 单人超过 12 条 | 某个孩子的口音会主导整份分数 |

自检把每一条闸各撞一次（`--self-test`，22 条），harness 里另有一条断言守着
「**每个拒收码都必须有对应的反例**」——加了闸不加反例，那条闸删掉也没人知道。

## 6. 从交付到落库：四步

```bash
cd apps/literacy-app

# 0. 交付清单照着这份填（sha256 是编的，只示范格式）
cat scripts/fixtures/asr/delivery-b1-example.json

# 1. 看批次 1 还差什么（只读，不写任何东西）
npm run ingest:asr:batch -- --plan

# 2. 演练：逐条过闸，打印哪些能进、哪些卡在哪一条上
npm run ingest:asr:batch -- --batch /mnt/controlled/B1/delivery-2026-09-12.json

# 3. 在拿着受控目录的那台机器上，顺带核对音频确实存在、sha256 对得上
npm run ingest:asr:batch -- --batch …/delivery.json --verify-audio /mnt/controlled

# 4. 确认无误再落库；有一条被拒就整份不落，不做部分落库
npm run ingest:asr:batch -- --batch …/delivery.json --apply
```

`--apply` 会做四件事，忘一件就会让数据说两套话：

1. `status` 改 `recorded`，挂上仓库外的音频指针 + `sha256` + `sampleRate`；
2. **删掉 `mock`**——真音频到了还留着模拟转写，真假指标迟早混进同一张表；
3. 孩子的 `consent` 落成 `signed`，并记下同意书编号 `consentRef`；
4. 进度现算：`freezeSet.recorded`、批次 `recorded`、`stage` 从 `skeleton` 推到 `recording`。

**它永远不做的三件事**：不碰 `available`（放行只有 Go/No-Go 一个入口）、
不把音频写进仓库、不替仲裁做决定。第三件写进了自检：落库产物里出现 `frozen` 就算失败。

### 类别漂移不是红灯

孩子读成什么样是录出来的，不是排出来的。`C059` 排的是 `normal`，孩子漏了个字，
交付里写 `"category": "miss"`——落库闸收下它，然后在汇总里报一行：

```
类别漂移（录出来的和排的不一样，不红灯但要在后两批配平）：miss +1 · normal -1
```

不红灯是因为你没法让孩子重读一遍还读成原来那样；报出来是因为批次 1 若整体往
`normal` 漂，剩下两批就得反向配平，而不是等 300 条录完才发现漏字样本只有一半。

## 7. 同意与合规

R13 只把「同意状态」做进了数据结构，流程本身没成文。这一轮把**能被执行的那部分**
落进了闸，剩下的仍是长尾：

| 项 | 状态 | 落在哪 |
|---|---|---|
| 逐条家长书面同意 | 落库硬前置：`consent[].state !== "signed"` 一律拒收 | 落库闸 `consent-missing` |
| 同意书编号可追溯 | 落库时写进 `clip.consentRef` | `asr-eval-set.json` |
| 撤回通道 | 改 `withdrawn` → harness 强制该孩子的条目清零；落库闸同时拒收他的新交付 | R13 断言 + 落库闸 |
| 音频存仓库外 | 路径写法上就拒绝仓库内指针 | 落库闸 `audio-in-repo` |
| 去标识化 | 孩子只以 `S01` 这样的编号出现；交付清单里不出现姓名 | §4 字段表（刻意没有姓名字段） |
| 保存期限 24 个月 | `consent.retentionMonths`，随包发出 | `asr-eval-set.json` |
| 同意书模板 / 删除时限的执行记录 | **仍未成文** | 见 §8 |

随包发到用户机器上的清单（`public/asr/manifest.json`）里只有**计数**：
批次号、槽位数、已录条数。受控目录路径、同意书编号、音频指针一个都不发——
`ROUND14_H1_SMOKE` 在构建产物里守这一条。

## 8. 已知局限

- **实录仍是 0/300。** 这一轮交的是派工单和收货台，不是货。任何把
  `recorded` 写成非零的改动，harness 的 `ROUND14_H1` post 断言当场红。
- **说话人 30 人，还差 10 人。** 单人 2–5 条看着安全，但 30 人的口音分布仍是偏的；
  扩到 40 人之前，任何子组差距都不要当真。
- **B2/B3 没排位。** 号段留了（C101–C300），槽位没排。原因是批次 1 的类别漂移
  会决定后两批怎么配平——现在排出来只会变成一张过期的表。
- **`--verify-audio` 在 CI 上跑不了。** 受控目录不在仓库里，CI 只能验元数据那一半；
  音频与 sha256 的核对必须在拿着目录的那台机器上跑一次，并把输出附进交付记录。
- **同意书模板与删除时限的执行记录仍未成文。** 这是 F4 真正的长尾，比录音本身更花时间。
  这一轮把「签了没」变成了一道门，没有把「怎么签、怎么删、谁来审」写出来。
- **真机 RTF（F7）一动没动。** 见 `.agent_workspace/r13-asr-android-rtf-baseline.md`，
  主机基准 `onDevice=false`，仍是 `[SKIP owner: Android QA]`。
